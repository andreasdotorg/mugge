## F-288: disko legacy MBR table warning — GPT migration not completed

**Severity:** medium
**Status:** open
**Found in:** `nix/nixos/disko.nix`
**Affects:** nixos-rebuild, SD card image build
**Found by:** owner (session 14, deploy output)

### Description

Every `nixos-rebuild switch` and `nix build` emits this warning:

```
evaluation warning: The legacy table is outdated and should not be used.
We recommend using the gpt type instead.
```

The disko configuration uses `type = "table"` (MBR) instead of `type = "gpt"`.
F-273 addressed partition label alignment but kept MBR. The assumption was that
Pi 4 requires MBR for boot compatibility, but this needs verification — the Pi 4
firmware can boot from GPT if the partition layout is correct (FAT32 first
partition).

### Questions to resolve

1. Can the Pi 4 boot from a GPT-partitioned SD card? (Pi 4 EEPROM with
   2024+ firmware supports GPT via the FAT32 partition discovery.)
2. Does disko's GPT type work correctly for the Pi 4 SD card image builder?
3. Are there any disko features (like the test framework) that require GPT?

### Fix required

Investigate GPT feasibility for Pi 4 boot. If GPT works, migrate `disko.nix`
from `type = "table"` to `type = "gpt"`. If MBR is truly required, document
why and suppress the warning.

### Research findings (session 16)

**Q1: Can Pi 4 boot from GPT?**

Yes, with caveats. The Pi 4 VideoCore bootloader (EEPROM firmware) discovers
the firmware partition by scanning for FAT partitions. The behavior depends on
the EEPROM version:

- **Pre-2020 EEPROM:** Only scans MBR partition types 0x0B/0x0C (W95 FAT32).
  GPT not supported.
- **2020-2023 EEPROM:** Added basic GPT support. The bootloader finds the FAT32
  partition via the GPT "Microsoft Basic Data" partition type GUID. However, some
  versions require the protective MBR to have partition type 0xEE.
- **2024+ EEPROM (pieeprom-2024-01-22 and later):** Robust GPT support. The
  bootloader scans GPT entries for any partition with a FAT filesystem. The FAT32
  firmware partition must be the first partition (lowest start LBA).

The Pi 4 Rev 1.2 in this project likely has a recent EEPROM (shipped 2020+), but
the exact version could not be determined — `rpi-eeprom-update` and `vcgencmd`
are not available on the NixOS image. The EEPROM version should be verified
before migration.

**Q2: Does disko's GPT type work for Pi 4 SD card?**

Yes. The disko `type = "gpt"` uses named partitions instead of the list-based
format used by `type = "table"`. Key differences:

- Partitions are defined as named attributes (not a list with start/end)
- Uses sgdisk instead of parted for partition creation
- Partition sizes use `size = "256M"` syntax instead of `start`/`end`
- GPT partition type GUIDs replace MBR type codes
- The `bootable` flag becomes an ESP flag or a legacy BIOS boot flag

The firmware partition would need:
- GPT type GUID: `C12A7328-F81F-11D2-BA4B-00A0C93EC93B` (EFI System Partition)
  or `EBD0A0A2-B9E5-4433-87C0-68B6B72699C7` (Microsoft Basic Data). The Pi 4
  bootloader recognizes both, but EFI SP is more conventional for boot partitions.
- FAT32 format with label FIRMWARE (unchanged)
- Must be the first partition

**Q3: Are there disko features that require GPT?**

Yes. The disko warning explicitly states: "certain features, such as the test
framework, may not function properly with the legacy table type." The test
framework validates partition layouts and may not work with MBR. Additionally,
the legacy table type is deprecated and may be removed in future disko versions.

**Recommendation:**

Migration to GPT is feasible and recommended, but requires:

1. **Verify EEPROM version** — install `raspberryPi.eeprom` or `vcgencmd` and
   check. If the EEPROM is pre-2020, update it first (can be done from the
   running system with `rpi-eeprom-update`).
2. **Test on a spare SD card first** — flash a GPT image, verify the Pi boots.
3. **Update both disko.nix AND repart-image.nix** — both deployment paths must
   use the same partition scheme (F-273 alignment requirement).
4. **Keep filesystem labels** — the `by-label/` mount strategy (F-273) works
   with both MBR and GPT, so the fileSystems entries don't need to change.

**Risk:** Low. The Pi 4 GPT boot path is well-tested in the community (Ubuntu,
Raspberry Pi OS 64-bit, and Fedora all ship GPT images for Pi 4). The main risk
is an old EEPROM that doesn't support GPT — easily mitigated by checking first.
