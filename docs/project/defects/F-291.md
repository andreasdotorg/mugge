## F-291: PipeWire running at SCHED_OTHER instead of SCHED_FIFO/88 on NixOS image

**Severity:** High
**Status:** RESOLVED
**Resolved by:** Session 16 revised fix (three-part: NNP re-enabled, PAM nice limit, mod.rt nice.level=0)
**Found in:** NixOS image (PipeWire systemd unit configuration)
**Affects:** All audio operation, all stories
**Found by:** worker-2 during US-155 deployment verification (session 15)

### Description

PipeWire on the Pi (192.168.178.35, NixOS image) was running at SCHED_OTHER
(nice -11) instead of the required SCHED_FIFO/88. The systemd override had
`CPUSchedulingPolicy=fifo` and `CPUSchedulingPriority=88`, but PipeWire's
internal RT module (`mod.rt`) was resetting scheduling back to SCHED_OTHER
during startup.

Journal showed on every PipeWire start:

```
mod.rt: could not set nice-level to -11: Permission denied
```

### Impact

RT scheduling is required for xrun-free audio under load. The system works at
low load but will fail under production conditions (DJ set, live performance).
This blocks reliable audio operation for all modes.

### Root Cause

PipeWire's `mod.rt` module performs two actions at startup:

1. `setpriority(nice.level=-11)` — set process nice level
2. `sched_setscheduler(SCHED_FIFO, rt.prio)` — set RT scheduling

On NixOS, no PAM nice limit existed for the audio user (`ela`), so step 1
failed with `EPERM`. **mod.rt's error handler treated any failure as fatal
and reset scheduling to SCHED_OTHER** — undoing systemd's pre-exec FIFO/88
that was already correctly applied.

### Session 15 Fix (WRONG — superseded)

Session 15 attempted to fix this by clearing `NoNewPrivileges` on the
PipeWire unit, reasoning that NNP was blocking RT promotion. This was
incorrect: with NNP cleared, `mod.rt` could call `sched_setscheduler()`,
but the nice failure still triggered the SCHED_OTHER reset. The fix appeared
to work only because `daemon-reload` was run during testing, which
temporarily masked the issue.

### Session 16 Fix (CORRECT — three-part)

The revised fix uses three complementary mechanisms:

**Fix A: RE-ENABLE NNP** (`nix/nixos/audio/pipewire.nix`)

NNP (`NoNewPrivileges=true`) is intentionally LEFT ENABLED on the PipeWire
unit (base unit default). With NNP=1, the kernel blocks `mod.rt`'s
`sched_setscheduler()` call in BOTH directions (promote AND demote). This
means `mod.rt` cannot interfere with systemd's pre-exec FIFO/88.
`CPUSchedulingPolicy=fifo` is applied by systemd PID 1 at exec time and is
exempt from NNP restrictions.

NNP also preserves the base unit's security hardening (seccomp, personality
lock, W^X).

**Fix B: PAM nice limit** (`nix/nixos/audio/pipewire.nix`)

```nix
security.pam.loginLimits = [
  { domain = "ela"; type = "-"; item = "nice";    value = "-19"; }
  { domain = "ela"; type = "-"; item = "rtprio";  value = "95"; }
  { domain = "ela"; type = "-"; item = "memlock"; value = "unlimited"; }
];
```

The nice limit (`-19`) allows `mod.rt`'s `setpriority(nice=-11)` call to
succeed. Without this limit, the call fails with EPERM, and `mod.rt`'s
error handler resets scheduling to SCHED_OTHER. With NNP=1, `mod.rt`
cannot call `sched_setscheduler()`, so FIFO/88 is safe regardless — the
nice limit only prevents `mod.rt`'s error cascade.

**Fix C: mod.rt nice.level override** (`configs/pipewire/11-rt-module.conf`)

```
context.properties = {
    module.rt.args = {
        nice.level = 0
        rt.prio    = 88
    }
}
```

Overrides `mod.rt`'s default `nice.level=-11` to `0`, preventing the
`setpriority()` call from failing even without PAM limits. Belt-and-suspenders
with Fix B. `rt.prio=88` matches systemd's pre-exec FIFO/88 for clarity,
though NNP blocks `mod.rt`'s `sched_setscheduler()` regardless.

### Why the three fixes work together

```
1. systemd PID 1 sets FIFO/88 at exec time (CPUSchedulingPolicy=fifo)
2. NNP=1 activates after exec — blocks sched_setscheduler() in BOTH directions
3. mod.rt starts, tries sched_setscheduler(FIFO/88) → blocked by NNP → no-op
4. mod.rt tries setpriority(nice=0) → succeeds (Fix C: nice.level=0, Fix B: PAM limit)
5. No error cascade → FIFO/88 preserved from step 1
```

### Verification

Validated after cold boot (session 16, no daemon-reload needed):

```bash
$ chrt -p $(pidof pipewire)
pid 678's current scheduling policy: SCHED_FIFO
pid 678's current scheduling priority: 88
```

- Zero `mod.rt` warnings in journal
- FIFO/88 survives cold boot without any manual intervention
- DJ load test (43 min, session 15): ~0.07 xruns/minute at FIFO/88
