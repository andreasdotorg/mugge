## F-293: NoNewPrivileges=true blocks SCHED_FIFO in graph-manager, signal-gen, pcm-bridge, level-bridge

**Severity:** Low (informational — latent hardening issue, not active failure)
**Status:** open
**Found in:** `nix/nixos/services/graph-manager.nix`, `nix/nixos/services/signal-gen.nix`,
`nix/nixos/services/pcm-bridge.nix`, `nix/nixos/services/level-bridge.nix`
**Affects:** Latent — `NoNewPrivileges` + `SystemCallFilter` conflict is a hardening
risk but not currently causing functional failures
**Found by:** AD (session 15, flagged during F-291 fix deployment)

### Description

All four Rust audio services have `NoNewPrivileges = true` in their systemd unit
configurations. This conflicts with `CPUSchedulingPolicy = "fifo"` if added later,
and with `SystemCallFilter` if RT self-promotion syscalls are attempted at runtime.

**This is NOT an active failure.** AD confirmed GraphManager is already running at
SCHED_FIFO/80 (set by the systemd unit's `CPUSchedulingPolicy` directive, which
takes effect before `NoNewPrivileges` locks down). The other three services
(signal-gen, pcm-bridge, level-bridge) do not currently request RT scheduling and
operate correctly at their default priority.

The risk is latent: if any service attempts runtime RT self-promotion (e.g., via
`sched_setscheduler()` syscall), `NoNewPrivileges` would silently block it. This
is a hardening inconsistency, not a functional bug.

### Fix (low priority)

1. Remove `NoNewPrivileges = true` from the four service units, or ensure
   `SystemCallFilter` allowlists include `sched_setscheduler` if runtime RT
   promotion is ever needed.
2. Consider adding explicit `CPUSchedulingPolicy = "fifo"` to signal-gen and
   pcm-bridge if RT scheduling proves beneficial for audio path reliability.
3. Compensate for the loss of `NoNewPrivileges` with other hardening options
   if needed (e.g., `ProtectSystem`, `ProtectHome`, `CapabilityBoundingSet`).
