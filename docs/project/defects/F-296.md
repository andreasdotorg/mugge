## F-296: Mixxx JACK bridge threads at SCHED_OTHER — xruns from missed RT deadlines

**Severity:** High
**Status:** RESOLVED (session 16)
**Found in:** NixOS Mixxx systemd service, NNP blocking mod.rt sched_setscheduler
**Affects:** DJ mode audio quality — Mixxx playback xruns
**Found by:** worker-2 (session 16, during F-295 diagnostics)

### Description

Mixxx's PipeWire JACK bridge threads (`pw-Mixxx`) were running at
`SCHED_OTHER` (normal priority) instead of `SCHED_FIFO` (real-time) on the
NixOS deployment. This caused ~3 ERR/min from the Mixxx node visible in
pw-top, with occasional audible clicks during DJ playback.

The Debian baseline had all Mixxx JACK threads at `SCHED_FIFO/83` via RTKit
promotion. On NixOS, the threads showed `SCHED_RESET_ON_FORK` — indicating
PipeWire's mod.rt attempted promotion but was blocked.

### Root Cause

Same mechanism as F-291: `NoNewPrivileges=true` (NNP) in the systemd service
blocks `sched_setscheduler()` calls. PipeWire's mod.rt module cannot promote
JACK client callback threads to RT scheduling when NNP is active.

The Mixxx systemd user service (`pi4audio-mixxx`) did not set
`CPUSchedulingPolicy` or `CPUSchedulingPriority`, so Mixxx launched at
`SCHED_OTHER`. When PipeWire's JACK bridge created `pw-Mixxx` threads,
mod.rt's attempt to promote them via `sched_setscheduler()` was blocked by
NNP, leaving them at `SCHED_OTHER` with `RESET_ON_FORK` flag set.

### Evidence

**Before fix — thread scheduling:**

| Thread | Policy | Priority | Notes |
|--------|--------|----------|-------|
| mixxx (main) | SCHED_OTHER | 0 | Normal priority |
| pw-Mixxx callback | SCHED_RESET_ON_FORK | 0 | Failed mod.rt promotion |
| pw-Mixxx callback | SCHED_RESET_ON_FORK | 0 | Failed mod.rt promotion |

**Debian baseline (for comparison):**

| Thread | Policy | Priority | Notes |
|--------|--------|----------|-------|
| mixxx (main) | SCHED_OTHER | 0 | Normal priority |
| pw-Mixxx callback | SCHED_FIFO | 83 | RTKit promotion |
| pw-Mixxx callback | SCHED_FIFO | 83 | RTKit promotion |

**pw-top ERR rate:** ~3 ERR/min from Mixxx node (contributed to overall ERR
alongside F-295 USB jitter).

### Resolution

**Fix:** Add `CPUSchedulingPolicy = "fifo"` and `CPUSchedulingPriority = 70`
to the Mixxx systemd user service (commit `87e4ab96`).

systemd sets the scheduling policy at exec time, before NNP activates. The
Mixxx process starts at FIFO/70, and pw-Mixxx JACK bridge threads inherit
the RT priority from the parent process.

**Priority 70** is below PipeWire (88) and GraphManager (80) but above
normal applications. This matches the JACK client thread priority hierarchy.

**After fix — thread scheduling:**

| Thread | Policy | Priority | Notes |
|--------|--------|----------|-------|
| mixxx (main) | SCHED_FIFO | 70 | systemd CPUSchedulingPolicy |
| pw-Mixxx callback | SCHED_FIFO\|RESET_ON_FORK | 70 | Inherited from parent |
| pw-Mixxx callback | SCHED_FIFO\|RESET_ON_FORK | 70 | Inherited from parent |

**Result:** Mixxx ERR eliminated from pw-top. Combined with F-295 period-num
fix, total system ERR rate dropped to ~1/min (acceptable, no audible clicks).

### Distinction from Other Defects

- **F-291** (RESOLVED): Same root cause mechanism (NNP blocks mod.rt) but
  for PipeWire itself. F-291 fix applied CPUSchedulingPolicy to PipeWire
  service. F-296 applies the same pattern to the Mixxx service.
- **F-295** (RESOLVED): USB isochronous jitter on VL805. Different root
  cause — ALSA buffer depth, not thread scheduling. Both contribute to ERR.
- **F-293** (OPEN): Same NNP issue affects graph-manager, signal-gen,
  pcm-bridge, level-bridge. Low priority — those services don't have
  RT-critical callback threads like JACK clients do.

### Related
